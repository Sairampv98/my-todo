| Tool         | Version used here | Check with        |
| ------------ | ----------------- | ----------------- |

| Code editor  | VS Code           | —                 |

> **Windows note that will bite you:** `localhost` on Windows resolves to `::1` (IPv6) *before*
> `127.0.0.1`. The stock MongoDB Windows install binds only IPv4 — its `mongod.cfg` contains
> `net: bindIp: 127.0.0.1` — so Node tries `::1`, gets no answer, and every query fails with
> `Operation 'todo.find()' buffering timed out after 10000ms`. This is not a code bug.
> Fix it either by starting MongoDB with `--bind_ip_all`, or by using `127.0.0.1` in `MONGO_URI`.
> To change the binding permanently, edit
> `C:\Program Files\MongoDB\Server\<version>\bin\mongod.cfg` → `net: bindIp:` and restart the
> MongoDB service. See Part 7 (Troubleshooting), row T1.

### Step 1.2 — Create the root `package.json` (npm workspaces)

The root `package.json` is the **external package** you asked for: one file that installs the
dependencies of both internal packages with a single `npm install`.

```json
{
  "name": "my-todo-app",
  "version": "1.0.0",
  "private": true,
  "description": "MERN Stack Todo application - BCA-V Semester capstone (MERN Stack Development)",
  "workspaces": [
    "backend",
    "frontend"
  ],
  "scripts": {
    "dev:backend": "npm run dev --workspace backend",
    "dev:frontend": "npm run dev --workspace frontend",
    "build": "npm run build --workspace frontend",
    "start": "npm run start --workspace backend",
    "lint": "npm run lint --workspace frontend"
  },
  "engines": {
    "node": ">=18"
  }
}
```

**What `"workspaces"` does:**

- One `npm install` at the root installs the dependencies of **both** `backend/` and `frontend/`.
- npm **hoists** shared packages into a single root `node_modules/`. There is no
  `backend/node_modules` and no `frontend/node_modules` — one copy of React, one of Express, one
  lockfile (`package-lock.json` at the root).
- `node_modules/backend` and `node_modules/frontend` become **symlinks** back to the folders, so
  the workspace packages can import each other by name.
- `npm run <script> --workspace <name>` runs a script inside one workspace.
- The per-folder `package-lock.json` files are **deleted** — with workspaces there is a single
  source of truth for the dependency tree.

```bash
npm install                        # once, at the root — installs everything
npm run dev:backend                # terminal 1 → http://localhost:8001
npm run dev:frontend               # terminal 2 → http://localhost:5173
npm run build                      # builds the frontend → frontend/dist
npm start                          # starts the backend in production mode
```

> **Where does the backend's `.env` come from under workspaces?** npm runs a workspace script with
> the working directory set to that workspace, so `backend/` is still the cwd and
> `dotenv.config({ path: "../.env" })` still resolves to the root `.env`. Verified working.

### Step 1.3 — Create the root `.env`

The `.env` file lives at the **root of the project**, one level above `backend/`.

```
MONGO_URI=mongodb://127.0.0.1:27017/todo
```

> Use a **single** slash before `todo`. `mongodb://localhost:27017//todo` silently creates a
> database whose name is literally `/todo` — the app appears to work but the collection path is
> wrong. This is a real trap; the "as-is" original had it.
>
> Use **`127.0.0.1`, not `localhost`**, on Windows. Windows resolves `localhost` to `::1` (IPv6)
> first, while the stock MongoDB install binds only IPv4 — the connection then hangs with
> `buffering timed out after 10000ms`. See Part 7, row T1.

Also commit a **`.env.example`** with the same key but no secrets, so students know what to fill in:

```
MONGO_URI=mongodb://127.0.0.1:27017/todo
```

When you move to a **cloud** cluster (MongoDB Atlas), replace that one line with the SRV string
Atlas gives you. Same key, different value:

```
MONGO_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/todo
```

> **Percent-encode the password.** If it contains `@ : / # ?` or `%`, encode it (`@` → `%40`,
> `:` → `%3A`, `/` → `%2F`, `#` → `%23`, `%` → `%25`) or the driver cuts the string short and
> reports an authentication error for a password that is actually correct.

> **If you see `querySrv ECONNREFUSED` against a cluster you know is healthy**, the problem is your
> machine's DNS, not Atlas. Add one more line to `.env` (fully explained in Step 2.3):
>
> ```
> DNS_SERVERS=8.8.8.8,202.88.156.6
> ```

### Step 2.1 — Initialise the backend package

```bash
cd backend
npm init -y
npm install express mongoose cors dotenv
```

> **No `nodemon` — the project uses Node's built-in watcher.** `node --watch src/server.js` (Node
> 18.11+) restarts the server when a file changes, with **zero extra dependencies**. Nodemon works
> too, but it drags in `chokidar` → `braces`, which currently carry a high-severity advisory, and
> npm's suggested fix is to downgrade nodemon to a 2017 release. A dev-only watcher is not worth
> three advisories and a broken suggestion:
>
> ```
> 3 high severity vulnerabilities
> fix available via `npm audit fix --force`
> Will install nodemon@1.14.10, which is a breaking change
> ```
>
> **Do not run `npm audit fix --force`.** Read what the advisory actually affects before you panic:
> `chokidar`/`braces` are only reachable through the dev watcher, and the production path
> (`npm start` → `node src/server.js`) never loads them. Forcing the fix would install a seven-year-old
> nodemon to silence a warning about code that does not ship. This is a great viva question — it is
> exactly the "dependency updates and vulnerability scanning" line in Module 6.

> **With workspaces, this still works.** npm looks upward, finds the root `package.json` with
> `"workspaces": ["backend", "frontend"]`, and installs the dependency into the `backend` workspace
> while updating the **root** lockfile. You end up with one `node_modules/` at the root — never a
> separate one inside `backend/`. The alternative, `npm install express mongoose cors dotenv
> --workspace backend` from the root, does exactly the same thing.

Your `package.json` must end up with these five runtime dependencies. `axios` and `bootstrap`
belong to the **frontend** only — do not install them here.

```json
{
  "name": "backend",
  "version": "1.0.0",
  "description": "",
  "main": "src/server.js",
  "scripts": {
    "dev": "node --watch src/server.js",
    "start": "node src/server.js"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "type": "module",
  "dependencies": {
    "cors": "^2.8.5",
    "dotenv": "^16.5.0",
    "express": "^4.18.2",
    "mongoose": "^8.14.3"
  }
}
```

Two things students get wrong here:

1. **`"type": "module"`** — without it Node treats every `.js` file as CommonJS and
   `import` throws `SyntaxError: Cannot use import statement outside a module`.
2. **`"main": "src/server.js"`** — the original said `"main": "server.js"`, a path that does not
   exist. It does not break `npm run dev` (that script names the file explicitly) but it breaks
   `npm start` and it misleads anyone reading the file.

### Step 2.2 — Create `src/Todo.js` (the Mongoose model)

This file is **Module 4** — data modelling and schema design.

```javascript
import mongoose from "mongoose";

const todoSchema = new mongoose.Schema({
    note: {
        type:String,
        required:true
    },
    content:{
        type:String
    }
});

const Todo = mongoose.model("Todo", todoSchema, "todo");

export default Todo;
```

Line by line:

- `new mongoose.Schema({...})` — describes the shape of one document.
- `required: true` on `note` — Mongoose refuses to save a todo with no note. This is
  **schema-level validation** and it fires before any database write.
- `mongoose.model("Todo", todoSchema, "todo")` — three arguments:
  1. `"Todo"` — the model name (used inside queries: `Todo.find()`),
  2. `todoSchema` — the schema it obeys,
  3. `"todo"` — the **collection name** in MongoDB. Without the third argument Mongoose would
     pluralise to `todos`. The spec says the collection is `todo`, so it is stated explicitly.

### Step 2.3 — Create `src/config.js` (the database connection)

```javascript
import mongoose from "mongoose";
import dotenv from "dotenv";
import dns from "node:dns";

// The .env file lives at the ROOT of the project (one level above backend/).
// When we run `npm run dev` from inside backend/, the process cwd is backend/,
// so "../.env" resolves to <project-root>/.env. The second call is a fallback
// for anyone who keeps a .env inside backend/ instead.
dotenv.config({ path: "../.env" });
dotenv.config();

/**
 * Point Node's DNS resolver at working nameservers, when the machine needs it.
 *
 * A `mongodb+srv://` URL is resolved with dns.resolveSrv(), which uses Node's
 * own DNS client (c-ares) - NOT the Windows resolver that your browser and
 * PowerShell use. On some networks, and whenever Windows "Mobile hotspot" /
 * Internet Connection Sharing is running, Node is told to ask 127.0.0.1, where a
 * stub resolver closes the connection instead of answering. The symptom is a
 * confusing "querySrv ECONNREFUSED" even though the cluster is healthy and DNS
 * works everywhere else on the same machine.
 *
 * Set DNS_SERVERS in .env to override it, for example:
 *   DNS_SERVERS=8.8.8.8,202.88.156.6
 *
 * Leave it unset on normal machines and on Render / Netlify - it changes nothing.
 */
const dnsServers = (process.env.DNS_SERVERS || "")
    .split(",")
    .map((server) => server.trim())
    .filter(Boolean);

if (dnsServers.length > 0) {
    dns.setServers(dnsServers);
    console.log(`DNS resolver set to: ${dnsServers.join(", ")}`);
}

/**
 * Connect to MongoDB, retrying with a backoff.
 *
 * A local MongoDB is ready in a few milliseconds. A cloud database (MongoDB
 * Atlas) is not: it needs a DNS lookup for the SRV record, a TLS handshake and
 * a replica-set discovery round trip - and the cluster can be briefly
 * unreachable while it fails over. So we retry a few times before giving up.
 *
 * @param {number} maxRetries how many attempts to make before exiting
 */
export const connectDB = async (maxRetries = 5) => {
    for (let attempt = 1; attempt <= maxRetries; attempt++) {
        try {
            await mongoose.connect(process.env.MONGO_URI, {
                // Fail fast instead of hanging, so the retry loop can take over.
                serverSelectionTimeoutMS: 10000,
                connectTimeoutMS: 10000,
                socketTimeoutMS: 45000,
            });
            console.log("Connected to the server");
            return;
        } catch (error) {
            console.error(
                `Database connection attempt ${attempt}/${maxRetries} failed: ${error.message}`
            );

            if (attempt === maxRetries) {
                console.error("Could not reach the database. Giving up.");
                process.exit(1);
            }

            // Linear backoff: wait 2s, then 4s, then 6s...
            const waitMs = attempt * 2000;
            console.log(`Retrying in ${waitMs / 1000}s...`);
            await new Promise((resolve) => setTimeout(resolve, waitMs));
        }
    }
};
```

> **Why two `dotenv.config()` calls?** The first one points at the root `.env`. The second one
> uses dotenv's default (`./.env` relative to the current working directory). dotenv never
> overwrites a variable that already exists, so the root file wins and the local file is only a
> fallback. Students who keep `.env` inside `backend/` still work.
>
> **Why is there a `DNS_SERVERS` override?** Because `mongodb+srv://` — and the rest of the
> internet — can be resolved by **two different resolvers on the same machine**:
>
> | Who | Which resolver | Where it is configured |
> | --- | -------------- | ---------------------- |
> | Your browser, `nslookup`, `ping` | the Windows DNS client | the Wi-Fi adapter |
> | Node's `dns.resolveSrv()` — used by the MongoDB driver for `mongodb+srv://` | **c-ares, inside Node** | `dns.getServers()` |
>
> When Windows "Mobile hotspot" / Internet Connection Sharing is running, Node is handed
> `127.0.0.1` as its nameserver. The stub resolver there closes the connection instead of
> answering, so the driver reports `querySrv ECONNREFUSED _mongodb._tcp.<cluster>.mongodb.net` —
> while the browser on the same machine resolves the very same name perfectly.
>
> The fix is one line in `.env`:
>
> ```
> DNS_SERVERS=8.8.8.8,202.88.156.6
> ```
>
> `dns.setServers()` changes **Node's** resolver only, and only when you set it. Leave it unset on
> a normal machine and on Render / Netlify, where the platform's DNS is already correct — the code
> does nothing at all.
>
> **Classroom value (10 minutes).** This is the classic "it works in my browser but not in the app"
> bug, and the reason every engineer needs two DNS tools in their toolbox:
> `nslookup <name>` (the Windows resolver) versus
> `node -e "require('node:dns').resolveSrv('<name>', console.log)"` (Node's resolver). If the two
> disagree, you have found it.

> **Why retry at all?** A local MongoDB is ready in milliseconds. A cloud database is not — it
> needs an SRV DNS lookup, a TLS handshake and a replica-set discovery round trip, and the cluster
> can be briefly unavailable while it fails over. The retry loop turns a transient network problem
> into a slow start instead of a crash.

> **Why the three timeouts?**

> ```javascript
> await mongoose.connect(process.env.MONGO_URI, {
>     serverSelectionTimeoutMS: 10000,  // how long to wait for a server to be found
>     connectTimeoutMS: 10000,          // how long the TCP/TLS handshake may take
>     socketTimeoutMS: 45000,           // how long a socket may sit idle before dying
> });
> ```

> `serverSelectionTimeoutMS` is the important one. Its default is 30 seconds — longer than the
> whole retry budget. Set it to 10 seconds and each attempt fails fast, so the loop can try again
> instead of hanging for half a minute.

> **Why `process.exit(1)`?** If the database is unreachable after every retry, the server must not
> pretend to be healthy. Exiting with a non-zero code makes the failure obvious in the terminal, and
> a hosting platform reads the exit code as "this instance is broken, replace it".

### Step 2.4 — Create `src/routes.js` (the routing table)

```javascript
import express from "express";
import {
    createTodo,
    deleteTodo,
    getAllTodo,
    getTodoById,
    updateTodo,
} from "./controller.js";

const router = express.Router();

//   GET    /todo        -> list all todos
//   GET    /todo/:id    -> fetch one todo
//   POST   /todo        -> create a todo
//   PUT    /todo/:id    -> update a todo

router.get("/", getAllTodo);

### Step 2.5 — Create `src/controller.js` (the business logic)

```javascript
import Todo from "./Todo.js";

export async function getAllTodo(req, res) {
    try {
        const todos = await Todo.find();
        console.log("Retrieved all notes from database");
        // Send the actual data back. res.json() is what reaches the frontend.
        res.status(200).json(todos);
    } catch (error) {
        console.error("Error in retrieving todo's error: ", error.message);
        res.status(500).json({ message: "Internal server error" });
    }
}

export const getTodoById = async (req, res) => {
    try {
        const todo = await Todo.findById(req.params.id);
        if (!todo) {
            return res.status(404).json({ message: "Todo not found" });
        }
        res.status(200).json(todo);
    } catch (error) {
        console.error("Error in retrieving the selected todo. Error: ", error.message);
        res.status(500).json({ message: "Internal server error" });
    }
};

export const createTodo = async (req, res) => {
    try {
        const { note, content } = req.body;
        const newTodo = new Todo({ note, content });
        const savedTodo = await newTodo.save();
        res.status(201).json(savedTodo);
    } catch (error) {
        console.error("Error in creating new todo. Error: ", error.message);
        res.status(500).json({ message: "Internal server error" });
    }
};

export const updateTodo = async (req, res) => {
    try {
        const { note, content } = req.body;
        const updatedTodo = await Todo.findByIdAndUpdate(
            req.params.id,
            { note, content },
            { new: true, runValidators: true }
        );
        if (!updatedTodo) {
            return res.status(404).json({ message: "Todo not found" });
        }
        res.status(200).json(updatedTodo);
    } catch (error) {
        console.error("Error in updating the selected todo. Error: ", error.message);
        res.status(500).json({ message: "Internal server error" });
    }
};

export const deleteTodo = async (req, res) => {
    try {
        const deletedTodo = await Todo.findByIdAndDelete(req.params.id);
        if (!deletedTodo) {
            return res.status(404).json({ message: "Todo not found" });
        }
        res.status(200).json({ message: "Deleted selected todo" });
    } catch (error) {
        console.error("Error in deleting the selected todo. Error: ", error.message);
        res.status(500).json({ message: "Internal server error" });
    }
};
```

Teaching points to extract from this file:

| Line                        | Concept                                                | Module |
| --------------------------- | ------------------------------------------------------ | ------ |
| `const { note, content } = req.body` | **Destructuring** — Module 1 JS recap          | 1, 3   |
| `await Todo.find()`         | Mongoose query returns a Promise                        | 4      |
| `res.status(200).json(todos)` | **Returning the data** — without this the UI gets nothing | 3, 5 |
| `new Todo({...}).save()`    | Create + validation in one step                         | 4      |
| `findByIdAndUpdate(..., {new:true})` | Return the *updated* doc, not the old one        | 4      |
| `runValidators: true`       | Run schema validation on updates too                    | 4      |
| `if (!todo) return 404`     | Handling a missing resource                             | 3      |
| `try ... catch` per handler | Error handling                                         | 3      |
| `res.status(500)` + generic message | Never leak stack traces to the client           | 3, 6   |

### Step 2.6 — Create `src/server.js` (the entry point)

```javascript
import express from "express";
import cors from "cors";
import mongoose from "mongoose";
import router from "./routes.js";
import dotenv from "dotenv";
import { connectDB } from "./config.js";

dotenv.config({ path: "../.env" });
dotenv.config();

const app = express();

// CORS: the React app runs on http://localhost:5173 and the API on :8001.
// Without this, the browser blocks every fetch as a cross-origin request.
app.use(cors());

// Middleware: lets Express parse a JSON body (req.body) for POST/PUT.
app.use(express.json());

// Health check. The hosting platform (Render) polls this to decide whether
// the service is up. It also reports the database state, so a service that is
// running but disconnected is visible instead of silently failing requests.
const DB_STATES = ["disconnected", "connected", "connecting", "disconnecting"];

app.get("/health", (req, res) => {
    const state = mongoose.connection.readyState;
    const ready = state === 1; // 1 === connected
    res.status(ready ? 200 : 503).json({
        status: ready ? "ok" : "degraded",
        database: DB_STATES[state] || "unknown",
    });
});

// Mount the router. Every route inside it is prefixed with /todo.
app.use("/todo", router);

/**
 * Start the server ONLY after the database is connected.
 *
 * This order matters. If we called app.listen() first, the server would accept
 * requests while Mongoose was still connecting, and every one of those
 * requests would fail with "buffering timed out after 10000ms". With a local
 * MongoDB the window is tiny; against MongoDB Atlas it is several seconds.
 */
const start = async () => {
    await connectDB();

    app.listen(8001, () => {
        console.log("Server is running on port 8001");
    });
};

start().catch((error) => {
    console.error("Failed to start the server:", error.message);
    process.exit(1);
});
```

Read this file as a **middleware pipeline** — that is exactly how Module 3 frames it:

```
request
   │
   ▼
cors()            → adds the CORS headers
   │
   ▼
express.json()    → parses the raw body into req.body
   │
   ▼
/health           → liveness + database state (used by the host platform)
   │
   ▼
/todo  router     → matches a route, runs the controller
   │
   ▼
response
```

#### The startup order — the most important line in this file

```javascript
const start = async () => {
    await connectDB();      // ← the database must be ready FIRST
    app.listen(8001, () => {
        console.log("Server is running on port 8001");
    });
};

start().catch((error) => {
    console.error("Failed to start the server:", error.message);
    process.exit(1);
});
```

**Why this matters, and why it bites hardest in the cloud.** Mongoose queues a query that arrives
before the connection is open, and after 10 seconds it gives up with:

```
Operation 'todo.find()' buffering timed out after 10000ms
```

Against a **local** MongoDB the connection takes a few milliseconds, so the window is invisible.
Against **MongoDB Atlas** the driver must first resolve an SRV record, complete a TLS handshake and
discover the replica set — a multi-second process. If the server starts listening *before* that
finishes, every request that arrives in the meantime fails.

So the rule is: **`app.listen()` must not run until `connectDB()` has resolved.** With `await`
in front of it, the server does not accept a single request until the database is actually
connected. If the database never comes up, `connectDB()` gives up and the process exits — the
service never pretends to be healthy.

> **Classroom demonstration (5 minutes, high value).** Point `MONGO_URI` at a dead port and start
> the server:
>
> ```
> Database connection attempt 1/5 failed: connect ECONNREFUSED 127.0.0.1:29999
> Retrying in 2s...
> Database connection attempt 2/5 failed: connect ECONNREFUSED 127.0.0.1:29999
> Retrying in 4s...
> ```
>
> Then, while it is retrying, try `curl http://localhost:8001/todo` from another terminal. You get
> **connection refused** — not a 500, not a buffering timeout. The server never accepted the
> request. That is the whole point: a request is either answered by a fully-connected service, or
> it never reaches the service at all.

#### The `/health` endpoint

```javascript
app.get("/health", (req, res) => {
    const state = mongoose.connection.readyState;
    const ready = state === 1; // 1 === connected
    res.status(ready ? 200 : 503).json({
        status: ready ? "ok" : "degraded",
        database: DB_STATES[state] || "unknown",
    });
});
```

`mongoose.connection.readyState` is a number with a fixed meaning:

| Value | State | Meaning |
| ----- | ----- | ------- |
| 0 | disconnected | not connected |
| 1 | connected | **ready to serve** |
| 2 | connecting | handshake in progress |
| 3 | disconnecting | shutting down |

The endpoint returns **200** when connected and **503** when not. Hosting platforms use that status
code to decide whether to route traffic to the service — Render polls `/health` (see `render.yaml`)
and restarts the service if it stops answering. It also means a service that is *running but
disconnected* shows up as `degraded` instead of silently 500-ing every request.

> `npm run build` on the trainer's machine and on any student's Windows laptop. Babel has no native

### Step 3.2 — Create `src/App.jsx`

```jsx
import { useState, useEffect } from "react";
import axios from "axios";
import 'bootstrap/dist/css/bootstrap.min.css';
import './App.css';

// The API base URL.
//
// Locally it falls back to the Express server on port 8001. In production you
// set VITE_API_URL to the ORIGIN of the deployed backend, for example
// https://todo-backend.onrender.com - the app appends /todo itself, so the
// variable never needs a path.
//
// Vite inlines VITE_ variables at BUILD time. So the variable must exist in
// the hosting platform's build environment, and the site must be REBUILT after
// you add or change it. Setting it only in the "Runtime" scope is not enough.
const API_BASE = import.meta.env.VITE_API_URL;
const API = `${API_BASE || "http://localhost:8001"}/todo`;

// A missing build-time variable is invisible until someone loads the page and
// sees an empty list. In a production build, no VITE_API_URL means the app is
// about to call http://localhost:8001 - a server that only exists on the
// machine that built it. So we say so, loudly, instead of failing quietly.
//
// The check skips localhost on purpose: when you preview a production build
// locally (npm run build, then npm run preview), http://localhost:8001 IS the
// backend, and warning about it would be wrong. On a deployed site the
// hostname is never localhost, so the warning always appears where it matters.
const MISSING_API_URL =
  import.meta.env.PROD &&
  !API_BASE &&
  !window.location.hostname.startsWith("localhost");

export default function App() {
  const [todos, setTodos] = useState([]);
  const [newTodo, setNewTodo] = useState("");
  const [content, setContent] = useState("");

  // Which todo is being viewed (full details) and which one is being edited.
  const [viewingId, setViewingId] = useState(null);
  const [editingId, setEditingId] = useState(null);
  const [editNote, setEditNote] = useState("");
  const [editContent, setEditContent] = useState("");

  // The last API failure, shown in the page. Without this, a failed request
  // and an empty database look exactly the same: a blank list.
  const [error, setError] = useState("");

  // Read - GET all todos from the API and store them in state.
  const fetchTodos = async () => {
    try {
      const res = await axios.get(API);
      setTodos(res.data);
      setError("");
    } catch (err) {
      console.error("Error fetching todos:", err.message);
      setError(err.message);
    }
  };

  // useEffect with an empty dependency array runs once, after the first render.
  useEffect(() => {
    fetchTodos();
  }, []);

  // Create - POST a new todo, then refresh the list.
  const addTodo = async (e) => {
    e.preventDefault();
    if (!newTodo.trim()) return;
    try {
      await axios.post(API, { note: newTodo, content });
      setNewTodo("");
      setContent("");
      setError("");
      fetchTodos();
    } catch (err) {
      console.error("Error adding todo:", err.message);
      setError(err.message);
    }
  };

  // Open the edit form for ONE todo, pre-filled with that todo's own values.
  const startEdit = (todo) => {
    setEditingId(todo._id);
    setEditNote(todo.note);
    setEditContent(todo.content || "");
    setViewingId(null);
  };

  // Close the edit form without saving.
  const cancelEdit = () => {
    setEditingId(null);
    setEditNote("");
    setEditContent("");
  };

  // Update - PUT the edited note AND content back to the server.
  const saveEdit = async (e) => {
    e.preventDefault();
    if (!editNote.trim()) return;
    try {
      await axios.put(`${API}/${editingId}`, {
        note: editNote,
        content: editContent,
      });
      cancelEdit();
      setError("");
      fetchTodos();
    } catch (err) {
      console.error("Error updating todo:", err.message);
      setError(err.message);
    }
  };

  // Show / hide the full details of one todo.
  const toggleView = (id) => {
    setViewingId(viewingId === id ? null : id);
  };

  // Delete - DELETE by id, then refresh the list.
  const deleteTodo = async (id) => {
    try {
      await axios.delete(`${API}/${id}`);
      setError("");
      fetchTodos();
    } catch (err) {
      console.error("Error deleting todo:", err.message);
      setError(err.message);
    }
  };

  return (
    <div className="container py-4" style={{ maxWidth: 720 }}>
      <h1 className="text-center mb-4">My Todo App</h1>

      {/* A configuration mistake must not look like an empty database. */}
      {MISSING_API_URL && (
        <div className="alert alert-danger">
          <strong>Configuration error.</strong> <code>VITE_API_URL</code> was not set
          when this site was built, so the app is trying to call{" "}
          <code>http://localhost:8001</code> — a server that exists only on the
          machine that built it. Set <code>VITE_API_URL</code> in your host&apos;s
          build environment (on Netlify: <em>Site configuration → Environment
          variables</em>, scope <em>Builds</em>), then redeploy the site.
        </div>
      )}

      {/* The API is unreachable — say so, instead of showing an empty list. */}
      {error && (
        <div className="alert alert-warning">
          <strong>Could not reach the API.</strong> <code>{error}</code>
        </div>
      )}

      <form onSubmit={addTodo} className="card p-3 mb-4 shadow-sm">
        <div className="mb-2">
          <label className="form-label">Note</label>
          <input
            type="text"
            className="form-control"
            placeholder="What needs to be done?"
            value={newTodo}
            onChange={(e) => setNewTodo(e.target.value)}
          />
        </div>
        <div className="mb-3">
          <label className="form-label">Content</label>
          <textarea
            className="form-control"
            rows="2"
            placeholder="Add a few details (optional)"
            value={content}
            onChange={(e) => setContent(e.target.value)}
          />
        </div>
        <button type="submit" className="btn btn-primary w-100">
          Add Todo
        </button>
      </form>

      <ul className="list-group shadow-sm">
        {todos.map((todo) => {
          const isViewing = viewingId === todo._id;
          const isEditing = editingId === todo._id;

          return (
            <li key={todo._id} className="list-group-item">
              <div className="d-flex justify-content-between align-items-start">
                <div className="flex-grow-1 me-3">
                  <strong>{todo.note}</strong>
                  {todo.content && !isEditing && !isViewing && (
                    <p className="mb-0 mt-1 todo-preview">{todo.content}</p>
                  )}
                </div>
                <div className="btn-group" role="group">
                  <button
                    type="button"
                    className="btn btn-sm btn-outline-secondary"
                    onClick={() => toggleView(todo._id)}
                  >
                    {isViewing ? "Hide" : "View"}
                  </button>
                  <button
                    type="button"
                    className="btn btn-sm btn-outline-warning"
                    onClick={() => startEdit(todo)}
                  >
                    Edit
                  </button>
                  <button
                    type="button"
                    className="btn btn-sm btn-outline-danger"
                    onClick={() => deleteTodo(todo._id)}
                  >
                    Delete
                  </button>
                </div>
              </div>

              {/* Full details - the readable version of the whole todo. */}
              {isViewing && (
                <div className="todo-details mt-3">
                  <div className="mb-2">
                    <span className="fw-semibold">Note: </span>
                    <span className="text-break">{todo.note}</span>
                  </div>
                  <div>
                    <span className="fw-semibold">Content: </span>
                    {todo.content ? (
                      <span className="text-break">{todo.content}</span>
                    ) : (
                      <span className="fst-italic">No content added for this todo.</span>
                    )}
                  </div>
                </div>
              )}

              {/* Edit form - both fields are editable here. */}
              {isEditing && (
                <form onSubmit={saveEdit} className="todo-details mt-3 p-3">
                  <div className="mb-2">
                    <label className="form-label">Note</label>
                    <input
                      type="text"
                      className="form-control"
                      value={editNote}
                      onChange={(e) => setEditNote(e.target.value)}
                    />
                  </div>
                  <div className="mb-3">
                    <label className="form-label">Content</label>
                    <textarea
                      className="form-control"
                      rows="3"
                      value={editContent}
                      onChange={(e) => setEditContent(e.target.value)}
                    />
                  </div>
                  <div className="d-flex gap-2">
                    <button type="submit" className="btn btn-sm btn-primary">
                      Save Changes
                    </button>
                    <button
                      type="button"
                      className="btn btn-sm btn-outline-secondary"
                      onClick={cancelEdit}
                    >
                      Cancel
                    </button>
                  </div>
                </form>
              )}
            </li>
          );
        })}
        {todos.length === 0 && (
          <li className="list-group-item text-center text-muted">
            No todos yet. Add your first one above.
          </li>
        )}
      </ul>
    </div>
  );
}
```

**Every Module-2 concept in this file, named:**

| Code                       | Concept                                  |
| -------------------------- | ---------------------------------------- |
| `export default function App()` | One component, function form        |
| `useState([])` / `useState("")` | State, one hook per value          |
| `value={newTodo} onChange={...}` | A **controlled** input                 |
| `useEffect(() => {...}, [])` | Run once after mount (fetch on load)    |
| `todos.map(todo => ...)`   | Rendering a list                        |
| `key={todo._id}`           | Stable key for list items                |
| `todos.length === 0 &&`    | Conditional rendering / empty state      |
| `e.preventDefault()`       | Stop the form from reloading the page    |
| `await axios.get(API)`     | Calling a REST API (Module 5)            |
| `setTodos(res.data)`       | Server data → UI                         |
| `viewingId` / `editingId`  | Tracking *which* item is open — one id per mode |
| `const isViewing = viewingId === todo._id` | Derived state per item      |
| `{isViewing && (...)}`     | Conditional rendering of a panel          |
| `startEdit(todo)`          | Loading one record into the edit form     |
| `editNote` / `editContent` | Two independent controlled inputs         |
| `todos.map(todo => { ... return (...) })` | The map body returns JSX, so it can use `const` |
| `const [error, setError] = useState("")` | Keeping the last failure in state, so the UI can show it |
| `import.meta.env.PROD` | True in a production build, false in `npm run dev` |
| `{MISSING_API_URL && (...)}` | Failing loudly when a build-time variable is missing |

> **Why call `fetchTodos()` again after every write?** It keeps one source of truth. The database
> is the source of truth; the UI is a mirror of it. This is simple, correct, and easy to explain.

> **Why does this app shout when it cannot reach the API?** Because an empty list is ambiguous. If
> the fetch fails, the old code logged to the console and rendered "No todos yet." — which is
> indistinguishable from a genuinely empty database. The user cannot tell a broken deployment from
> a working one. Now the component keeps the failure in `state` and shows it.
>
> The same idea drives the `MISSING_API_URL` guard: in a **production** build with no
> `VITE_API_URL`, the app is about to call `http://localhost:8001` — a server that exists only on
> the machine that built it — so it says exactly that, in the page, instead of failing quietly.
>
> **This is the single most useful habit in a deployment.** A build-time configuration mistake is
> invisible until someone loads the site. *Fail fast, fail loud, and fail in the place the user is
> looking.* It also turns a ten-minute DevTools investigation into a two-second read.

> **Why not `window.prompt` for editing?** A prompt returns **one string**, so it can only ever
> edit one field. The original draft used it and lost the `content` on every save. It also
> prefilled from the wrong piece of state — the *add form's* value instead of the selected todo's.
> An inline edit form with two controlled inputs is barely more code and edits everything. This is
> the single most common beginner mistake in a CRUD app: **a form that edits one field is not a
> form that edits the record.**

| 9 | The build toolchain was `@vitejs/plugin-react-swc` — a native Rust binary | `npm run build` failed on Windows with `Error: Failed to load native binding`. `@swc/core@1.16.x` validates the permissions of every ancestor of its cache directory and rejects the AppContainer SID that `C:\` grants, so it cannot be worked around from the project side. | Switch to `@vitejs/plugin-react` (Babel, pure JavaScript) in both `package.json` and `vite.config.js` — see Step 3.1 | 1, 6 |
| 10 | `connectDB()` was called **without `await`**, so `app.listen()` ran immediately | On localhost the window is a few milliseconds and you never notice. Against MongoDB Atlas the connection takes seconds, and every request in that window failed with `Operation 'todo.find()' buffering timed out after 10000ms`. The comment in the file even claimed the opposite of what the code did. | `await connectDB()` before `app.listen()` inside an async `start()`, plus a retry loop with backoff — see Steps 2.3 and 2.6 | 3, 6 |
| 11 | The code assumed Node's DNS resolver and the Windows resolver are the same thing | `querySrv ECONNREFUSED _mongodb._tcp.<cluster>.mongodb.net` against a **perfectly healthy** Atlas cluster — while the browser, `nslookup` and PowerShell resolved the same name fine. Two more that were **not** runtime bugs but were still wrong:

| Defect | Why it matters |
| ------ | -------------- |
| `"main": "server.js"` in `backend/package.json` | That file does not exist. Breaks `npm start`, misleads readers. |
| `MONGO_URI =mongodb://localhost:27017//todo` | The double slash makes the database name literally `/todo`. Works by accident, wrong by design. |

> **Classroom use:** give students the broken version and ask them to find the eleven bugs. It
> teaches more than showing them the finished code, and it is exactly the "debug student code"
> competency an interview panel probes.
>
> **Defect #7 is the best one to teach.** It is not a crash — it *looks* like it works. The user
> clicks Edit, types a new note, saves, and the note changes. The content silently disappears,
> and nothing in the UI says so. Ask students: "what would a test for this look like?" (It is the
> classic argument for asserting on the whole response body, not just the status code.)
>
> **Defect #10 is the best one for a cloud deployment.** It never appears locally, because the
> local database connects in milliseconds. It only shows up once you deploy — and then it looks
> like "Atlas is slow" rather than "our code starts the server too early". Teaching students to
> suspect *their own startup sequence* rather than the platform is the lesson.
>
> **Defect #11 is the best one for teaching debugging.** The evidence contradicts itself: the
> browser resolves the hostname, the server does not. That is the moment a student learns to stop
> trusting the browser tab and start reading the resolver. Ask them to run `nslookup` and then
> `node -e "require('node:dns').resolveSrv('...', console.log)"` side by side — two commands, and
> the mystery is over.

## Part 11 — Deployment (Module 6)

Three pieces, three different services:

```
   GitHub repo
        │
        ├──► Netlify  ──►  frontend/dist   (static React app)
        │      ▲
        │      │  VITE_API_URL = https://todo-backend.onrender.com
        ▼      │
   Render ──►  backend (Express)  ──►  MongoDB Atlas
              ▲
              │  MONGO_URI = mongodb+srv://...   (set in the Render dashboard)
```

### Step 11.1 — What `dist/` is

`npm run build` runs Vite's production build. It compiles the JSX, bundles React, Bootstrap and
Axios into one file, minifies it, and writes the result to `frontend/dist/`:

```
frontend/dist/
├── index.html                 0.4 KB   ← the entry page
├── vite.svg                   1.5 KB   ← the favicon
└── assets/
    ├── index-XXXXXXXX.css   226.3 KB   ← Bootstrap + your styles, minified
    └── index-XXXXXXXX.js    272.0 KB   ← React + your app code, minified
```

`dist/` is **generated output**, not source. It is listed in `.gitignore` and is never committed —
Netlify and Vercel rebuild it from source on every push. The filenames contain a content hash
(`index-W7npi5gf.js`), so the filename changes whenever the content changes, which is how the
browser cache is invalidated.

> **Teaching point:** the "dist" name is the same convention as `dist/` in webpack, Angular and
> older CRA projects. "Build output goes in `dist/`" is a near-universal rule worth stating once.

### Step 11.2 — Make the API URL configurable

A hardcoded `http://localhost:8001` in the frontend would make the deployed site point at the
*user's own laptop*. Change `App.jsx` to read an environment variable:

```javascript
// The API base URL.
// Locally it falls back to the Express server on port 8001. In production you
// set VITE_API_URL to the deployed backend URL (Netlify / Vercel environment
// variable) and the same build works against the live API.
const API = import.meta.env.VITE_API_URL || "http://localhost:8001/todo";
```

Vite only exposes variables prefixed with `VITE_` to the browser, and it **inlines them at build
time** — they are public, so never put a secret here. A database password must stay on the server.

### Step 11.3 — Deploy the frontend to Netlify

Create `netlify.toml` at the **repository root**:

```toml
[build]
  base = "frontend"
  command = "npm run build"
  publish = "dist"

[build.environment]
  NODE_VERSION = "22"

# Single-page application: every unknown path is served by index.html so that
# React Router routes (added in Module 6) work on a hard refresh.
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

> **The one rule that trips everyone up:** Netlify resolves `publish` **relative to `base`**. With
> `base = "frontend"` and `publish = "dist"`, Netlify publishes `frontend/dist`. Writing
> `publish = "frontend/dist"` here would make Netlify look for `frontend/frontend/dist` and fail
> with *publish directory not found*.

Then in Netlify:

1. **Add new site → Import an existing project** → pick the GitHub repo.
2. Netlify reads `netlify.toml` automatically — the build command and publish directory are filled
   in for you.
3. **Site configuration → Environment variables** → add `VITE_API_URL` =
   `https://<your-backend>.onrender.com`.
4. **Deploy site.** Every push to `main` triggers a rebuild.

### Step 11.4 — Deploy the frontend to Vercel instead

1. **Add New → Project** → import the repo.
2. Set **Root Directory** to `frontend` (Vercel then reads `frontend/vercel.json`).
3. Framework preset: **Vite**. Build command `npm run build`, output `dist`.
4. **Settings → Environment Variables** → `VITE_API_URL` = the backend URL.

`frontend/vercel.json` makes this explicit:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "vite",
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "installCommand": "npm install"
}
```

### Step 11.5 — Deploy the backend to Render

`render.yaml` at the repository root:

```yaml
services:
  - type: web
    name: todo-backend
    runtime: node
    rootDir: backend
    buildCommand: npm install
    startCommand: npm start
    healthCheckPath: /health
    envVars:
      - key: NODE_VERSION
        value: "22"
      - key: MONGO_URI
        sync: false
```

`MONGO_URI` has `sync: false`, which means Render **prompts you for it** instead of reading it from
the file. That is deliberate: a connection string contains a database password and must never be
committed to Git. Paste your MongoDB Atlas URI into the Render dashboard.

`npm start` runs `node src/server.js` — the same code, without the watch mode.

`healthCheckPath: /health` matters more than it looks. Render polls that URL to decide whether the
service is alive. Point it at `/todo` and a database outage looks like a healthy service that
returns 500s; point it at `/health` and the platform sees a **503** and replaces the instance.

### Step 11.6 — The MongoDB piece

Use **MongoDB Atlas** (the free tier is enough for a class project):

1. Create a free M0 cluster.
2. **Database Access** → add a user with a password.
3. **Network Access** → allow access from anywhere (`0.0.0.0/0`) so Render can reach it.
4. Copy the SRV connection string and put it in `.env` locally and in the Render dashboard.

```
MONGO_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/todo?retryWrites=true&w=majority
```

#### Are the two strings really interchangeable? Yes — in the code

`mongoose.connect()` is the same call for both. The **only** thing that changes is the string in
`process.env.MONGO_URI`. Nothing in `config.js`, `controller.js` or `Todo.js` knows or cares which
database it is talking to. That is the clearest possible demonstration that **the connection string
is configuration, not code** (Module 3: "environment variables and config").

| | Local | Atlas |
| --- | --- | --- |
| Form | `mongodb://127.0.0.1:27017/todo` | `mongodb+srv://user:pass@cluster.mongodb.net/todo` |
| Host resolution | a literal IP | a DNS **SRV lookup** — one hostname, many backend nodes |
| TLS | off by default | **on by default** with `mongodb+srv://` |
| Replica set | standalone | a real replica set — `retryWrites` and `w=majority` are meaningful |
| Startup time | ~50 ms | **seconds** (SRV + TLS + replica-set discovery) |

That last row is exactly why the startup order matters. On a local database, `app.listen()` before
`connectDB()` resolves is a race you will never notice. Against Atlas it is a multi-second window
where every incoming request fails with a buffering timeout. `await connectDB()` first, and the
problem does not exist at any scale.

#### Three Atlas traps that cost everyone an hour

1. **The password must be URL-encoded.** Atlas passwords often contain `@ : / # ?` — all of which
   are meaningful in a URI. Encode them: `@` → `%40`, `:` → `%3A`, `/` → `%2F`, `#` → `%23`,
   `?` → `%3F`. Otherwise you get `MongoServerError: Authentication failed` with a password you
   are certain is correct.
2. **The IP Access List.** Atlas refuses connections from addresses that are not on the list. Add
   the host's outbound IP, or `0.0.0.0/0` for a class project.
3. **The database name is the path, not a query parameter.** `...mongodb.net/todo` creates the
   database `todo`; `...mongodb.net/?db=todo` is not how it works. And a **double slash** creates
   a database literally named `/todo`, which MongoDB then rejects.

#### Verify the connection before deploying the frontend

```bash
# local .env pointing at Atlas
node -e "const m=require('mongoose');m.connect(process.env.MONGO_URI,{serverSelectionTimeoutMS:10000}).then(async()=>{console.log('Atlas OK');await m.disconnect()}).catch(e=>{console.log('FAIL:',e.message)})"
```

If that prints `Atlas OK`, the credentials, the encoding and the IP list are all correct — and the
only thing left to get wrong is the frontend's `VITE_API_URL`.

### Step 11.7 — After deploying, check these

[ ]  The Netlify URL loads and shows "My Todo App"
[ ]  Browser console has no CORS error
[ ]  https://<backend>.onrender.com/health returns 200 {"status":"ok","database":"connected"}
[ ]  Adding a todo works from the deployed site

### Step 11.8 — Deployment troubleshooting

#### Which variable goes where

There are **two hosts** and **two variables**. Putting either in the wrong place is the single
most common deployment mistake, so get this table into your head before you start:

| Variable | Lives on | Read by | Value | Scope |
| -------- | -------- | ------- | ----- | ----- |
| `MONGO_URI` | **Render** (the backend) | `backend/src/config.js` | your Atlas SRV string | Runtime |
| `VITE_API_URL` | **Netlify / Vercel** (the frontend) | `frontend/src/App.jsx` | `https://<backend>.onrender.com` | **Builds** |
| `.env` (local) | your machine, gitignored | both, via dotenv | local values | — |

- The **backend** talks to the database → the database URI belongs on the backend host.
- The **frontend** talks to the backend → the backend URL belongs on the frontend host.
- The frontend host **never** needs the database URI. Putting it there is not just useless, it
  puts a database password one careless `VITE_`-prefix mistake away from being published.

`VITE_API_URL` is the **origin only** — no `/todo`. The app appends it:

```javascript
const API = `${import.meta.env.VITE_API_URL || "http://localhost:8001"}/todo`;
```

#### The symptom table

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| The Network tab shows `http://localhost:8001/todo` on the deployed site | `VITE_API_URL` was not set **when Netlify built the site**, so Vite inlined the localhost fallback | Set `VITE_API_URL` in Netlify (Builds scope) and **redeploy** |
| The Network tab shows `(failed) net::ERR_CONNECTION_REFUSED` for a request to `http://localhost:8001/todo` | The browser is trying to reach **your own machine**, because the built bundle still contains the localhost fallback. Nothing is wrong with the server — the request never left the visitor's computer | Same fix: set `VITE_API_URL` in Netlify (Builds scope) and redeploy. Confirm with the DevTools → Network → **Headers → Request URL** row |
| `MONGO_URI` is set on **Netlify** | The database URI was put on the frontend host. The backend runs on Render, so Netlify never reads it — and a database password does not belong in a build environment | **Delete** `MONGO_URI` from Netlify and set it in **Render**'s dashboard instead. Netlify needs only `VITE_API_URL` |
| The deployed site works on your laptop but not for a classmate | The deployed bundle still points at `localhost` — i.e. at *your* machine | Same fix. Verify the **built JS**, not the source |
| You changed `VITE_API_URL` and nothing happened | Vite inlines `VITE_` variables at **build** time. A restart is not enough — the site must be **rebuilt** | Trigger a new deploy (push a commit, or Netlify → *Deploys* → *Retry deploy*) |
| The variable is set but the build still uses localhost | It was added only in the **Runtime** scope | Netlify: set it with the **Builds, Functions, Runtime** scope selected |
| `MONGODB_URI` is set on Netlify | Wrong **name** and wrong **host** | The backend reads `MONGO_URI`. Put it in **Render**, and delete it from Netlify |
| `MongooseServerSelectionError` in the Render logs | `MONGO_URI` missing, renamed, or the password is not URL-encoded | Rename to `MONGO_URI`; percent-encode the password |
| Render logs: `Could not reach the database. Giving up.` | Atlas refused the connection | Check the Atlas **IP Access List** and the encoded password |
| CORS error in the browser console on the deployed site | `app.use(cors())` is missing or below the router | It must be registered **before** `app.use("/todo", router)` |
| `/health` returns `503` on Render | The database is not connected | Fix the Atlas connection first — nothing else matters yet |
| Netlify: *publish directory not found* | `publish` was written as `frontend/dist` | `publish` is relative to `base`, so with `base = "frontend"` it must be `dist` |
| The deployed site shows the app but the list is empty | The backend is reachable but the database is not | Check `/health`, then the Atlas connection |
| `vite: not recognized` right after you pushed to GitHub | `git clean -xdf` deleted the gitignored `node_modules/` before the push. Netlify installs its own — your machine no longer has any | `npm install` **at the repository root**, then `npm run build`. Use `git clean -nd` (dry run) first, or `git clean -xdf -e node_modules` |

#### The bundle-hash check — proof in one glance

Vite names the output file after a hash of its contents, so **the filename tells you whether the
variable reached the build**:

| Build | Output file |
| ----- | ----------- |
| No `VITE_API_URL` (the broken case) | `assets/index-DypnbcgB.js` |
| `VITE_API_URL=https://todo-backend.onrender.com` | `assets/index-BJF5kXxr.js` |

The Netlify build log prints the same line. If your log shows the *no-variable* filename, the
variable never reached the build — no amount of redeploying without setting it will help. Compare
the log against the table above and the answer is immediate.

#### How to verify the fix instead of guessing

Do not eyeball the source — **read what was actually built**:

```bash
# locally, reproduce what the host does
VITE_API_URL=https://todo-backend.onrender.com npm run build

# then look inside the bundle
grep -o "localhost:8001\|onrender\.com" frontend/dist/assets/*.js | sort -u
```

Expected output when it is right:

```
onrender.com
```

and **no** `localhost:8001`. If `localhost:8001` is still there, the variable never reached the
build. On the deployed site, the same check is `View Source` on `index.html`, then open the
`assets/index-*.js` file and search it for `localhost:8001`.

> **The single most valuable habit in this whole module:** when a deployed app misbehaves, verify
> the **build output**, not the source you wrote. The source is what you *meant*; the bundle is
> what the browser will actually run. This is the same instinct as checking `/health` before
> opening the browser — both are "look at the thing that is really running, not a copy of it".
